## Why this run exists (added 2026-09-30, real user request)

A real case: an approved plan to exclude Instagram Feed placement failed execution because Meta's API rejected one value in it (`facebook_stories` isn't a valid `facebook_positions` value). Nothing wrong happened — marketing-lead correctly stopped rather than guess a fix, verified no partial write occurred, and logged the failure with a follow-up for media-buyer to correct it. But the very next chance for the system to notice and act on that was the *next day's* daily heartbeat — a live problem (halved CTR, real money) would have sat uncorrected for up to 24 hours longer than necessary just because of when in the day it happened to fail. Suraj's framing: *"the system should check for anything failed... so we can fix it there and then and dont have to waste a day."*

## What this run is

Narrow and cheap — not a general anomaly pull (that's the daily heartbeat) and not a full account review (that's the weekly review). Your only job:

1. **Find today's failures.** Read `knowledge/learning-log.jsonl` for every entry dated **today** whose `subject` or `summary` indicates a failed execution attempt (e.g. contains "FAILED", "execution attempt... FAILED", "could not be executed", "rejected"/"error" from a live write call) — this is deliberately a text-pattern check across today's entries, not a query against a fixed list of known failure phrasings, since a new kind of failure should still be caught. Cross-check `~/ka-meta-ads/telegram_approvals_state.json` for any entry with `"status": "failed"` too, same day.
2. **Skip anything already resolved.** If a later entry today already `linked_to` the failure and represents a corrected plan sent for approval, or the failure was already handed off and is awaiting Suraj's own input (not the system's), there's nothing to do — don't re-dispatch work that's already in flight.
3. **For each genuinely still-open failure, drive it to a corrected, ready-to-approve plan today.** Read the failure's own `follow_up` field — it already states which agent owns the correction (per marketing-lead's execution-failure handling, this is always the validating agent, e.g. media-buyer for an execution-plan defect, not a redesign from scratch). Dispatch that agent with the failure's exact evidence (the real API error, the rejected value, what still needs fixing) so it can independently re-validate against Meta's current API and produce a corrected plan — same standard as any other plan (fresh live re-verification, no reused stale assumptions). If the fix requires a fact only Suraj can confirm (not just a technical re-validation), say so plainly and route as a question instead of guessing.
4. **Send the corrected plan for approval today**, via `scripts/send-telegram-approval.sh <plan-id>`, same as any other ready `type: decision` plan (`docs/proactive-operations.md` §8a) — this is the whole point of the run: close the loop same-day instead of waiting for tomorrow morning.
5. **No failures found today, or everything already in flight:** stop here, no notification, no log entry — same "don't log what confirms nothing changed" principle as every other run. A quiet run is a correct, expected outcome, not a failure to find something.

## Hard boundaries — identical to the daily heartbeat, no exceptions here either

- **Never dispatch marketing-lead's execution protocol. Never call any Meta/Instagram write endpoint.** Every call this run makes must be `GET` only. This run corrects and re-validates *plans* — it never re-attempts the failed write itself. The retry only happens after Suraj approves the corrected plan, same as any first attempt.
- All learning-log writes go through `scripts/append-learning-log.sh` — never a raw file edit or `echo >>`. If it exits non-zero, the entry did **not** land; say so plainly.
- Don't manufacture urgency where there isn't any — if a failure's own follow_up shows it's waiting on Suraj (not the system), don't nag with a duplicate notification; the daily/weekly due-now sweep already covers that case on its own cadence.
